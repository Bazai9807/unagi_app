# UNAGI Platform backend · 0.2.0

Общий API для Android/iOS и кабинеты оператора платформы и владельца бизнеса. **Это локальная версия для проверки; весь production-функционал ещё не завершён.** Реальная отправка заказов намеренно закрыта сервером. Сохранение настроек интеграции не включает приём платежей или списание бонусов.

## Быстрый запуск на Windows и Mac

Нужен Node.js 24 LTS. Дополнительная установка PostgreSQL для локальной проверки не требуется: используется PGlite (PostgreSQL в WASM), данные сохраняются в `.data/postgres/`.

```sh
cd backend
npm ci
npm run setup
npm start
```

- Панель платформы: http://127.0.0.1:4300/platform
- Кабинет бизнеса: http://127.0.0.1:4300/business
- Сгенерированные пароли: `.local-access.txt` (локальный файл, не включается в Git).
- Повторный `setup` сохраняет существующих пользователей и данные. Пароли случайные, не одинаковые на двух компьютерах.
- Секрет шифрования создаётся в `.env`; сохранить его отдельно от резервной копии базы. При потере ключа расшифровка интеграционных доступов невозможна.
- Начальные бренды/точки UNAGI условные: `UNAGI · бренд 1/2/3`. Не выдавать их за реальные названия заведения.

Локальные базы Windows и Mac разные. GitHub синхронизирует исходники, но не базы, `.env`, аккаунты, пароли и сессии. После развёртывания оба клиента будут обращаться к общему серверу.

## Что реально реализовано

- PostgreSQL-совместимая схема и транзакции; локальный PGlite либо `DATABASE_URL` для обычного PostgreSQL.
- Модель бизнес → бренд → точка, раздельные записи по бизнесам, серверные права пяти ролей.
- Сотрудники, безопасное хранение паролей scrypt, серверные сессии с HttpOnly/SameSite cookie, CSRF, ограничение попыток входа, TOTP 2FA с защитой от повторного кода.
- Вход покупателя по собственному исходящему звонку: адаптер SMS.RU Callcheck, временная проверка, секрет конкретной попытки, проверка результата на сервере, одноразовое получение сессии. Без ключа сервис отвечает ошибкой настройки, а не авторизует покупателя.
- Бренды, точки, переключатели получения, параметры доставки, тип подтверждения заказа, лимиты бонусов, способы оплаты и соответствия ID iiko.
- Редактор цветов/оформления, сохранённый черновик, публикация, последние 30 версий и откат. Опубликованные настройки доступны через публичный API; установленное ранее мобильное приложение ещё не читает этот API.
- Тестовый цикл заказа: расчёт по серверному каталогу, идемпотентность, контроль переходов состояния, журнал, тестовые оплата/возврат. Реальные финансовые операции не выполняются.
- Аналитика по периодам и брендам: суммы, средний выполненный заказ, отмены, возвраты, дни, часы, точки, способы получения/оплаты, товары. Отдельный выбор live/sandbox, экспорт CSV с защитой от формул.
- История тарифов (подписка/процент), ежемесячные счета, ручное подтверждение оплаты услуг, очередь напоминаний и SMTP worker. Самостоятельного отключения при просрочке нет.
- Ручные ограничения новых заказов, оформления и акций с причиной и аудитом. Старые заказы остаются доступны.
- Зашифрованное хранение ключей iiko/Т-Банка. Read-only проверка организаций и получение сырого снимка внешнего меню iiko. Прикладная нормализация/публикация реального меню пока не выполнена.
- Подготовлены криптографические функции Token и HTTP-адаптер методов Т-Банка; Token проверен по официальному примеру. Это ещё не завершённый платёжный процесс.

## Что пока НЕ реализовано/НЕ подключено

1. Сопоставление реального меню: организации/терминалы/категории цен, размеры, обязательные модификаторы, стоп-листы. Снимок iiko не становится активным каталогом автоматически.
2. Создание и изменение реального заказа в iiko, проверка результата команды, восстановление неизвестного результата, получение актуальных статусов и webhooks.
3. Реальная расчётная сессия iikoCard, баланс, резерв/списание/возврат бонусов и действующие промокоды. Сохранённые лимиты не подменяют расчёт iikoCard. Бонусный balance возвращается `null`, а не фиктивный ноль.
4. Полный процесс эквайринга: Init/СБП QR, обработчик уведомлений, сверка, фискальные чеки и возвраты. Вызовы адаптера из клиентского API пока не открыты.
5. Проверка геозон, расписания праздников, загрузки кухни, брони стола и интервалов доставки. В текущем тестовом калькуляторе применяются только включённые способы, минимумы и тариф доставки; часы сохранены как настройки.
6. Связь реального Android/iOS клиента с этим сервером, вход по звонку в мобильном UI, защищённое хранение сессии и открытие платёжного браузера. Текущее приложение остаётся офлайн-демо.
7. Push-уведомления, полноценный CMS баннеров/загрузки изображений, кабинет обращений покупателей, отчёты о себестоимости/воронке/удержании без соответствующих источников данных.
8. Public production deployment, миграция реальных данных, проверка восстановления backup, ротация ключей, самостоятельное восстановление пароля и 2FA, полная эксплуатационная наблюдаемость. Веб-журнал сейчас показывает аудит действий, а технические ошибки пишутся обезличенно в stderr.

**Не открывать этот прототип для реальных покупателей.** Блокировка `liveOrders: false` в `src/config.js` снимается только после реализации и тестирования перечисленных критичных сценариев, а не простым переключением переменной.

## Проверки

```sh
npm test
```

Тесты запускают настоящий PostgreSQL engine в памяти и HTTP API через Fastify inject. Проверяются межклиентская изоляция, роли, CSRF, подмена цен/товаров, конкурирующие повторы заказа, состояния, ограничения, публикация оформления, шифрование, счета/письма, разделение аналитики, звонок с неправильным proof/tenant, одноразовость входа, TOTP и Token Т-Банка.

UI проверяется в браузере отдельно. Настоящие внешние вызовы в тестах не производятся, проверки провайдера звонков моделируются ответами API.

## Письма

Worker раз в минуту формирует напоминания по просроченным неоплаченным счетам, не более одного на счёт за UTC-день. Отправка только при `ENABLE_EMAIL=true` и настроенном SMTP. По умолчанию письма остаются в очереди.

Счета сейчас создаёт оператор вручную по месяцу. Реальные начисления процента считаются только по завершённым месяцам и выполненным live-заказам; подписка — по тарифу на начало месяца. Стоимость внедрения хранится в тарифе, но отдельный счёт на внедрение пока не создаётся. Смена тарифа начинается с первого числа месяца; корректировки прошлого периода требуют отдельного процесса.

Неопределённый результат SMTP помечается `unknown` и не повторяется вслепую. Перед повтором нужно свериться с почтовым провайдером. Зависшие после сбоя `sending` также требуют проверки. SPF/DKIM/DMARC настраиваются для реального домена перед включением отправки.

## Сервер и настройки

Файл `.env.example` перечисляет параметры. Для production необходимы HTTPS `PUBLIC_ORIGIN`, `DATABASE_URL`, стабильный `ENCRYPTION_KEY`, отдельный пользователь PostgreSQL и постоянное хранилище. Не использовать локальные тестовые аккаунты и `.data` как production-инфраструктуру.

Предполагается один экземпляр API/worker до настройки распределённых ограничений запросов и эксплуатации. Админская проверка Origin требует точного совпадения с PUBLIC_ORIGIN. `trustProxy` выключен: при настройке обратного прокси нужно явно доверить только его адреса; иначе лимит IP будет общим для пользователей за прокси. Не включать произвольный trustProxy.

Схема создаётся идемпотентно из `sql/001-schema.sql`. До следующих изменений схемы добавить версионированные миграции и проверку их применения. Для production необходима отдельная процедура создания первого администратора; demo `setup` в production запрещён.
